第一次照着文档写 AI API 调用代码的时候，很多人会在参数列表里看到一个叫 `stream` 的选项，默认是 `false`，改成 `true` 之后返回结果的方式完全不一样，但文档往往只说"是否启用流式响应"，没说清楚新手到底该选哪个。这篇文章不讲技术实现原理，只讲一件事：你的场景应该开还是不开。

## 一、两者的区别，用点餐来打比方

想象你在餐厂点了一份套餐：

- **非流式（`stream: false`）**：后厨把整份套餐做完，一次性端上桌。你在厨房把菜做好之前什么都看不到，但端上来的时候是完整的一整份。
- **流式（`stream: true`）**：后厨做好一道菜就先给你端一道，你可以边等边吃前面做好的部分，不用等全部做完才能开始。

对应到 AI API 上：非流式是等模型把整段回复全部生成完，服务器才把结果一次性返回给你；流式是模型每生成一小段文字，就立刻推给你一段，你能一个字一个字（或一个词一个词）地看到内容"打字机式"地出现——这也是为什么 ChatGPT、Claude 这些聊天界面里,文字都是一点点蹦出来的,而不是等半天突然刷出一整段。

## 二、什么时候该选非流式

以下场景选非流式更省心：

- **你要处理的是结构化数据**，比如让模型返回一个 JSON 对象，你需要拿到完整、能直接解析的结果，中途拿到半截 JSON 毫无用处
- **调用是在后台脚本里跑的**，没有用户在盯着屏幕等，比如批量给 1000 篇文章生成摘要，这种场景用户根本看不到"打字过程"，流式带来的体验提升是零
- **你还在学习阶段，先把功能跑通**：非流式的代码逻辑更简单——发请求、等结果、拿到手直接用，不用处理"结果分成好多段陆续到达"这件麻烦事。先用非流式把整个功能跑通，之后有需要再改成流式，是更稳妥的学习路径

## 三、什么时候该选流式

以下场景流式几乎是必选项：

- **做聊天界面、对话类产品**：用户提问后，如果要等模型把几百字的回答全部生成完才显示，等待感会很强烈，容易让人以为"卡住了"。流式让文字一点点出现，用户能立刻感知到"系统在响应"，等待体验完全不同
- **生成内容比较长**：模型回复超过几百字时，非流式意味着用户要盯着一片空白等好几秒甚至十几秒，流式则是从第一个字开始就有内容展示，实际等待时间没变,但感知等待时间大幅缩短
- **需要支持用户中途打断**：比如用户发现 AI 跑题了，想直接停止生成换个问法，流式响应可以在任意时刻中断连接，非流式必须等模型把整段生成完才能拿到（哪怕你不要了）

## 四、新手最容易踩的两个坑

**坑一：以为流式响应更快**。流式不会让模型生成内容的总时间变短，模型该花多久生成完整回复还是花多久,流式只是把"一次性等待"拆成了"分批到达",总耗时基本相同,变化的只是你什么时候能看到第一个字。如果你的目标是"减少总响应时间"，该优化的是模型选择或 prompt 长度,而不是切换 stream 参数。

**坑二：流式返回的内容处理起来更麻烦，新手常常代码写错**。非流式拿到的是一个完整对象，直接读字段就行；流式拿到的是一连串"事件"（每次推送一小块），需要在代码里把这些小块拼接起来、处理连接中断、处理消息传到一半却断开的情况。如果你是刚学 API 调用，建议先看官方 SDK 有没有现成的流式处理封装（大多数官方 SDK 都有），不要自己从零手写 SSE 解析逻辑，容易漏处理边界情况。

## 五、一张选择表

| 你的场景 | 建议 |
|---|---|
| 做给用户看的聊天对话产品 | 流式 |
| 生成内容比较长（几百字以上） | 流式 |
| 后台批量处理任务，无人盯屏幕 | 非流式 |
| 需要结构化 JSON 输出直接解析 | 非流式 |
| 刚开始学习，先把功能跑通 | 非流式，跑通后再升级 |
| 用户需要能随时打断生成 | 流式 |

拿不准的时候，记住一个简单原则：**有真人用户在实时等结果，就用流式；没人盯着看、或者需要完整结构化数据才能用，就用非流式**。
