登录循环是最让人没头绪的一类故障：没有任何报错，页面也不卡，就是点完「登录」之后一闪，又回到了输邮箱的那一页。因为没有报错文案可查，很多人就在「重启浏览器—换节点—重装」之间来回转。

这类问题的根因只有三层：登录凭证没能存下来（浏览器侧）、存下来了但请求没带上或被中断（网络侧）、带上了但服务端不认（账号侧）。按这个顺序查，每一层都有一个能明确给出「是/不是」的动作，不需要靠猜。

## 一、先用一个动作分出大方向

打开浏览器的开发者工具（F12 或右键「检查」），切到 Network 面板，勾上「Preserve log」保留日志，然后完整走一次登录。

看登录完成那一刻跳转的那个请求：

| 观察到的现象 | 大方向 |
|---|---|
| 登录接口返回 200，但紧接着的页面请求又跳到 /login | 凭证没存下或没带上 → 第二、三节 |
| 登录接口本身返回 401 / 403 | 服务端不认 → 第五节 |
| 登录接口一直 pending 最后超时 | 网络中断 → 第四节 |
| 请求里完全看不到 Cookie 头 | 浏览器侧拦截 → 第二节 |

这一步花不到两分钟，能直接砍掉三分之二的排查范围。下面按层展开。

## 二、浏览器侧：凭证没能存下来

登录状态靠 Cookie 维持。只要 Cookie 写不进去，登录就一定循环，而且不会有任何报错——服务端以为写成功了，浏览器那边其实丢了。

常见的四个原因，按出现频率排：

1. **第三方 Cookie 被完全阻止**。Safari 的「阻止所有跨站跟踪」、Firefox 的严格模式、各类隐私插件都会导致这个结果。登录流程里有跨域跳转，这些策略会把中间环节的 Cookie 丢掉。
2. **系统时间不准**。Cookie 带过期时间，本机时间比实际快，浏览器会认为刚下发的 Cookie 已经过期，立即丢弃。偏差超过几分钟就可能触发。这一条最隐蔽，也最容易修——打开系统设置里的自动同步时间即可。
3. **浏览器存储已满或配置文件损坏**。表现是不止 Claude，别的网站也零星掉登录。
4. **广告拦截类插件误伤**。拦截规则更新后偶尔会误拦认证域名下的请求。

逐条验证的顺序：先开无痕窗口并关掉所有插件试一次。无痕下正常 → 问题在插件或主配置文件的存储上，逐个关插件定位；无痕下仍然循环 → 跳过这一节，去第四节。

顺带一句，多设备同时登录本身不会导致循环，但会导致较早的会话被挤掉，表现成「过一会儿又要重新登录」，和登录循环不是一回事。两者的区别在[多设备登录](/blog/cn-ai-account-multi-device-login/)那篇里写过。

## 三、登录方式本身的差异

用 Google 账号登录和用邮箱验证码登录，走的是两套流程，卡住的位置也不同：

```
邮箱验证码登录
  填邮箱 → 收码 → 填码 → 签发会话 Cookie → 跳转主页
  ^ 容易卡在「收码」和「签发 Cookie」两步

Google / 第三方登录
  点按钮 → 跳转 Google → 授权 → 带 code 跳回 → 换取会话 → 跳转主页
  ^ 多了两次跨域跳转，容易卡在「带 code 跳回」这一步
```

所以一个很有效的交叉验证：如果你平时用 Google 登录，改用邮箱验证码再试一次；反之也成立。两种方式只有一种循环，说明问题出在跨域跳转环节（多半还是第二节的 Cookie 策略）；两种都循环，问题在更靠后的层。

要注意的是，**不要为了试而把同一个邮箱同时绑到两种登录方式上来回切**，容易把账号搞成两个独立身份、历史对话对不上。两种登录方式各自的取舍可以参考[Google 还是邮箱登录](/blog/cn-chatgpt-google-apple-login-choice/)，那篇讲的是 ChatGPT，但机制一样。

邮箱验证码根本收不到是另一个独立问题，处理方式在[Claude 邮箱验证码收不到](/blog/cn-claude-email-code-not-received/)。

## 四、网络侧：请求中断或来源不一致

无痕模式下仍然循环，大概率在这一层。核心机制是：Claude 的会话校验会参考请求的来源一致性，如果登录那一刻和后续请求看起来来自完全不同的地方，会话会被判为无效。

具体表现为三种情况：

- **出口 IP 在登录过程中发生了变化**。很多代理工具默认按连接负载均衡，同一次登录的几个请求可能从不同出口发出。把模式改成固定单一节点，再试一次——这是这一层最常见的原因。
- **DNS 与代理走向不一致**。页面能打开说明主域名解析没问题，但认证相关的域名如果走了不同路径，就会出现「首页正常、登录循环」。
- **长连接被中间设备切断**。登录接口一直 pending 最后超时，属于这一类。

还有一种容易混淆的情况：如果你的出口国家本身不在服务范围，通常会是整页拦截而不是登录循环。两者的区别和判定依据写在[Claude 提示所在地区不支持](/blog/cn-claude-supported-region-error/)那篇；真的是整页拦截就去看那篇，别在这一层耗时间。

国内网络环境下这几类问题的通用排查，见[国内网络环境排查](/blog/cn-network-troubleshooting/)。

## 五、账号侧：服务端明确不认

如果登录接口直接返回 401 或 403，或者前面几层全部排除之后仍然循环，问题在账号本身。这一层的判断方法很直接：**换一台设备、换一个网络、用另一个账号登录**。

| 另一个账号 | 你的账号 | 结论 |
|---|---|---|
| 正常 | 循环 | 账号侧有问题 |
| 也循环 | 循环 | 设备或网络环境的问题，回到第二、四节 |

确认是账号侧之后，能做的只有一件事：用注册邮箱向官方提交申诉，说明情况并等待处理。这里要特别强调两点：

1. **不要反复重试登录**。短时间内大量失败的登录尝试本身就是风控信号，越试越难恢复。
2. **不要为了「绕过」去注册小号**。同一设备、同一网络下批量注册会把设备和网络一起标记，连带影响原本正常的账号。

至于「清缓存、重装浏览器」这类动作，只在第二节那一层有意义。确认是账号侧之后再折腾本机，纯属浪费时间。

## 六、按层对应的处理清单

把上面压成一张可以照着做的表：

| 层 | 验证动作 | 如果命中怎么做 |
|---|---|---|
| 浏览器 | 无痕 + 关插件登录一次 | 逐个关插件定位；同步系统时间 |
| 浏览器 | 看请求里有没有 Cookie 头 | 放宽第三方 Cookie 策略 |
| 登录方式 | 换另一种登录方式试 | 只有一种循环 → 回到 Cookie 策略 |
| 网络 | 固定单一节点再登一次 | 关掉代理的负载均衡/自动切换 |
| 网络 | 看登录接口是否 pending 超时 | 换线路类型（住宅/机房）验证 |
| 账号 | 换设备 + 换网络 + 换账号 | 只有你的账号循环 → 走官方申诉 |

顺序别跳。每一层的现象会掩盖下一层的现象，从上往下走才不会误判。
