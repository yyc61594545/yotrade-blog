"Batch API 比实时调用便宜 50%"，这个数字在站内的 [Batch API 真实省钱测算](/blog/llm-batch-api-real-savings/)和[《Batch 与实时调用的成本临界点》](/blog/llm-batch-vs-realtime-cost/)里已经用真实账单算过很多遍了，本文不再重复这部分计算。

但很多团队按这个数字算完账、决定"全面切 Batch"之后，会发现实际省下来的钱比预期少——因为账单上的单价差异，只是成本差的一部分。这篇文章补上另一半：那些不会出现在账单上、但确确实实要花钱花人力的隐性成本。

## 一、账单成本：站内已有的结论，直接引用

先给一个简版结论，方便本文后续对比：

| 维度 | Batch API | 实时调用 |
|---|---|---|
| 单价 | 通常便宜 40%-50% | 标准价 |
| 返回时效 | 数分钟到 24 小时（各家承诺不同） | 秒级 |
| 适用场景 | 离线任务：标注、翻译、批量摘要 | 用户可见的交互场景 |

具体到 OpenAI、Anthropic 各家的折扣比例、真实账单案例，以及"调用量多大才值得切"的临界点计算，站内文章已经讲得很细，这里不重复展开，直接看上面两篇即可。本文要算的是**单价之外的成本**。

## 二、隐性成本一：工程改造

把一个实时调用的功能改成批处理，不是把 `stream: true` 改成 `false` 那么简单，通常要新增：

- **任务队列**：请求不再是"发出去立刻拿结果"，需要一个地方存放"已提交、等结果"的任务状态
- **轮询或回调机制**：批处理任务完成时间不确定，要么定期轮询状态接口，要么接收 webhook 回调，两者都要写额外代码和处理失败重试
- **结果拼接与分发**：批处理返回的是一个结果文件（通常是 JSONL），需要解析后按原始请求 ID 分发回对应的业务流程
- **超时与降级逻辑**：如果批处理任务超过预期时间没完成，要不要降级成实时调用？这条分支很多团队一开始会漏掉

这部分改造的人力成本，对一个已有稳定实时调用链路的团队来说，往往是一次性的 3-10 人天，具体格式细节可以参考[《LLM Batch API 的 JSONL 格式详解》](/blog/llm-jsonl-batch-format/)。如果调用量不大，这笔一次性投入可能比省下来的 API 费用还高，这也是很多小团队"知道 Batch 更便宜，但没切"的真实原因。

## 三、隐性成本二：延迟带来的业务成本

Batch API 的返回时间通常是"尽力而为"，不是 SLA 承诺的固定时长。这意味着：

- 需要给业务方设定合理预期（"今天提交的翻译任务，明天才能拿到结果"），而不是默认它和实时调用一样快
- 如果批处理任务恰好卡在处理队列高峰期，实际耗时可能远超平时经验值，业务侧需要有应对预案
- 对时效敏感的场景（比如需要当天见效的客服话术优化），批处理省下的钱可能远不如"晚一天上线"造成的业务损失

延迟本身不是"额外花的钱"，但换算成"业务因为等待而错失的价值"，也是决策时该放进天平的一部分，只是很难用一个统一的数字量化，需要按具体场景估算。

## 四、隐性成本三：监控与运维复杂度

实时调用出问题，通常能立刻在监控里看到（错误率、延迟飙升）。批处理任务的失败模式不一样：

- 任务提交成功，但处理过程中部分子任务失败，需要专门的"部分失败"处理逻辑，不能简单地"成功/失败"二分
- 批处理任务的可观测性通常弱于实时调用（没有实时的 P99 延迟曲线），排查问题更依赖事后查日志
- 需要额外的监控规则："提交后 N 小时还没返回"要不要告警，这是实时调用里不存在的运维负担

如果团队已经有比较成熟的成本异常监控体系，可以参考[《LLM 成本异常检测》](/blog/llm-cost-anomaly-detection/)里的思路，把批处理任务的"超时未返回"也纳入告警范围，而不是等业务方来问"我的任务去哪了"。

## 五、一个更完整的决策框架

把账单成本和隐性成本放到一起，判断是否值得切 Batch，可以按这个顺序自查：

1. **单价差值够不够大**：先按[《Batch 与实时调用的成本临界点》](/blog/llm-batch-vs-realtime-cost/)里的框架算一遍，月调用量小的团队，省下的绝对金额可能覆盖不了改造成本
2. **场景是否真的能接受延迟**：如果业务方嘴上说"能接受慢一点"，但实际每次都追着问结果好了没，说明这个场景本质上还是实时需求，硬切 Batch 只会制造摩擦
3. **是否已有队列和轮询基础设施**：如果团队已经有成熟的异步任务系统（比如已经在用消息队列做其他异步任务），改造成本会大幅降低，性价比随之上升
4. **失败重试的成本能不能接受**：批处理任务失败后，重新提交意味着又要等一轮返回时间，比实时调用"失败立刻重试"的代价更高，任务越关键，这一条权重越大

四条里如果有两条以上是"否"，即便账单上 Batch 更便宜，也不一定是当前阶段该做的优化——不如先看看[《LLM 成本优化清单》](/blog/llm-cost-optimization-checklist/)里其他优先级更高、改造成本更低的项。
