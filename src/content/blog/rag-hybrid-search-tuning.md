纯向量检索在 RAG 系统里有个众所周知的短板：对精确匹配（人名、型号、错误码、专有名词）不敏感，因为这些 token 在 embedding 空间里的区分度往往不如语义相近但字面不同的内容。反过来，纯关键词检索（BM25 之类）又抓不住语义相似但用词不同的查询。Hybrid Search 把两者结合，理论上取长补短,但真正的难点从来不是"要不要做 hybrid"，而是**权重怎么配**——这篇文章聚焦调优本身,前提是你已经决定要做混合检索,只是不知道怎么把权重调对。

## 一、先搞清楚要融合的是"分数"还是"排名"

Hybrid Search 有两种融合思路，选错会让后续调优事倍功半：

**分数融合（Score Fusion）**：把向量相似度分数和 BM25 分数做加权求和。问题是两者量纲完全不同——余弦相似度在 0~1 之间，BM25 分数理论上无上限且分布随语料库变化。直接加权求和前必须做归一化，而归一化方法本身就会引入偏差（min-max 归一化对离群值敏感，z-score 归一化需要知道分布)。

**排名融合（Rank Fusion）**：不看具体分数，只看每个文档在两个检索结果里的排名，用 Reciprocal Rank Fusion（RRF）之类的算法合并。RRF 的公式很简单：

```
RRF_score(d) = Σ 1 / (k + rank_i(d))
```

其中 `rank_i(d)` 是文档 d 在第 i 个检索器结果里的排名，`k` 是一个平滑常数（常用 60）。RRF 的好处是不需要处理量纲不一致的问题，工程上更稳健，也是目前大多数生产系统的默认选择。**建议没有特殊理由就直接用 RRF，不要自己发明分数融合公式**——分数融合调起来的参数敏感度远高于 RRF，投入产出比低。

## 二、RRF 里唯一要调的参数：k 值和检索器权重

标准 RRF 假设两个检索器同等重要，但实践中语义检索和关键词检索的可靠度往往不对等，需要加权版本：

```
RRF_score(d) = Σ w_i / (k + rank_i(d))
```

`w_i` 就是每个检索器的权重。调优的核心工作就是找到合适的 `w_vector` 和 `w_keyword` 配比。经验起点：

| 查询特征 | 建议权重倾向 |
|---|---|
| 查询里含精确术语（型号、代码、专有名词） | 关键词检索权重更高 |
| 查询是自然语言问句、口语化描述 | 向量检索权重更高 |
| 文档库是技术文档、API 参考 | 关键词检索权重适当提高 |
| 文档库是长文叙述性内容（如博客、FAQ） | 向量检索权重适当提高 |

`k` 值的作用是控制排名靠后的文档对最终分数的影响程度——`k` 越小，排名差异被放大得越明显；`k` 越大，融合结果越平滑，头部差异被压缩。多数场景下 `k=60` 是够用的默认值，不需要单独调，优先把精力放在 `w_i` 的调优上。

## 三、静态权重的天花板：为什么要做动态权重

固定权重（比如永远 0.5:0.5 或者 0.7:0.3）能覆盖大部分查询，但会在两类查询上明显失手：

- 一个包含精确错误码的查询，用固定的语义偏重权重，关键词检索命中的最相关文档可能被稀释到融合结果的后排
- 一个纯语义问句用固定的关键词偏重权重，同理会漏掉真正相关但用词不同的文档

动态权重的思路是先对查询做一个轻量分类，再选择对应的权重配置。一个可落地的实现：

```python
def get_weights(query: str) -> tuple[float, float]:
    # 简单启发式：含精确匹配特征词的查询提高关键词权重
    has_exact_pattern = bool(
        re.search(r'[A-Z0-9\-_]{4,}|"\w+"', query)  # 型号/代码/引号内精确词
    )
    if has_exact_pattern:
        return (0.3, 0.7)  # (向量权重, 关键词权重)
    return (0.7, 0.3)
```

更精细的方案可以用一个小模型做查询意图分类（"事实查找型" vs "语义理解型"），但在大多数场景下，正则规则加一些启发式特征已经能覆盖 80% 的收益，不需要一开始就上模型分类器。

## 四、没有评估集，调权重就是猜

权重调优最大的坑是"凭感觉试几个数字，看着顺眼就上线"。没有评估集,每次调整都是盲调,而且没法量化到底是不是真的变好了。最低限度需要准备：

1. **一批真实查询**：从生产日志里抽取，覆盖精确匹配型和语义理解型两类，各不少于 30 条
2. **每条查询标注相关文档**：至少标出 Top-3 应该召回哪些文档 ID，人工标注即可，不需要复杂工具
3. **评估指标**：优先看 Recall@5 和 MRR（Mean Reciprocal Rank），这两个指标对检索质量的区分度比单纯的准确率更有意义

调优流程应该是：固定评估集 → 跑不同权重组合 → 比较指标 → 选最优组合。可以参考 [RAG 分块策略评估方法](/blog/rag-chunking-evaluation/) 里评估集构建的思路，两者评估集其实可以复用，只是评估维度不同（一个测分块粒度，一个测检索权重）。

## 五、一个容易被忽视的变量：重排序（Reranking）会掩盖权重问题

如果 pipeline 里 Hybrid Search 之后还接了一层 Cross-Encoder 重排序，很多团队会觉得"反正后面有重排，前面权重随便调调也没事"。这个假设有风险：重排序模型只能对**已经召回**的候选集重新排序，如果 Hybrid Search 阶段权重配错导致关键文档根本没进入候选集（比如候选集只取 Top-20），重排序再强也无力回天。

正确的心智模型是：**Hybrid Search 权重决定召回的"天花板"，重排序决定召回集合内部的排序精度**。调优权重时应该单独评估 Hybrid Search 阶段的 Recall@K（K 取重排序前的候选集大小，比如 20），而不是只看最终呈现给用户的 Top-3 效果，否则很难判断问题出在检索阶段还是重排序阶段。

## 六、调优检查清单

实操中建议按这个顺序推进，避免同时改多个变量导致无法归因：

1. 先确认用 RRF 而不是分数融合
2. 用固定权重（如 0.5:0.5）跑通评估集，记录基线 Recall@5 和 MRR
3. 分别单独调高向量权重、单独调高关键词权重，观察指标变化方向
4. 如果两类查询表现差异明显，引入动态权重分类逻辑
5. 检查候选集大小是否足够大，确认重排序前的 Recall@K 达标
6. 上线后持续用真实查询日志扩充评估集，权重不是调一次就永久固定的
