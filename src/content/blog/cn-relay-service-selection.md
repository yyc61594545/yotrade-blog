国内中转服务市场的格局与趋势,可参考[《国内 LLM 中转服务市场观察》](/blog/cn-llm-relay-market-overview/)。选定要用中转之后,真正的难题往往是:面对十几家看起来功能都差不多的服务商,**该盯着哪几个指标做对比,而不是被营销话术带节奏**。本文把选型拆成六个可量化打分的维度,给出每个维度的具体检验方法。

## 一、稳定性:不要只看官方宣传的可用性数字

几乎所有中转服务的宣传页都会写"99.9% 可用性",但这个数字往往是自己统计、自己发布,参考价值有限。更可靠的做法是自己动手测:

- **拉长观察窗口**:至少连续观察 1-2 周,而不是试用几个小时就下结论。中转服务的稳定性问题经常集中在特定时段(比如国内晚高峰、上游厂商限流窗口期),短时间测试容易漏掉
- **关注错误类型而非只看错误率**:同样是 5% 的失败率,是均匀分布的偶发超时,还是集中在某几个时间段的整体不可用,对业务影响完全不同。具体的稳定性测试方法可参考[《AI API 中转稳定性测试方法》](/blog/ai-api-relay-stability-test/)
- **看服务商是否提供可验证的历史状态页**:公开、可追溯、由第三方监控(而非自己写页面自己填数据)的状态页,可信度明显更高

如果不想自己长期盯着测,也可以参考[《中转服务可用性自助监控方案》](/blog/cn-ai-relay-uptime-monitoring/)里的方法,搭一个轻量监控脚本,把候选的几家服务商放在一起跑对比。

## 二、延迟:P50 之外一定要看 P99

延迟指标最容易被"平均数陷阱"误导。一家服务商可能平均延迟很低,但尾部延迟(P99)很差,意味着大部分时候快,但总有一小部分请求慢得离谱——这种波动对用户体验的伤害往往比"整体慢一点但很稳定"更大。

选型时至少要拿到或自测三个数字:P50(中位数)、P95、P99,三者差距越小说明延迟越稳定。同类横评数据可参考[《LLM P99 延迟横评》](/blog/llm-p99-latency-comparison/),但注意这类横评测的是特定时间点、特定网络环境下的数据,自己的业务场景(部署地域、并发量)不同,结果可能有出入,建议以自测为准。

## 三、模型覆盖广度与更新速度

| 检查项 | 怎么判断 |
|---|---|
| 覆盖的模型家族数量 | 是否只覆盖 1-2 家(如仅 OpenAI),还是同时覆盖 OpenAI/Anthropic/Google/国内主流模型 |
| 新模型上线速度 | 上游厂商发布新模型后,中转服务多久能跟进接入——可以查其更新日志或公告频道的历史记录 |
| 是否支持模型的完整能力 | 有些中转只透传基础对话能力,新出的能力(如某些高级工具调用参数、扩展思维模式)未必第一时间跟进,用之前问清楚 |
| 接口协议统一度 | 是否统一成一套(如 OpenAI 兼容格式)调用所有模型,还是不同模型要用不同的请求格式 |

模型覆盖广度不是越多越好,而是要匹配自己实际会用到的模型——如果只用 Claude 和 GPT 两家,不需要为"覆盖 20 家模型"这个卖点额外付费。

## 四、计费透明度:警惕"看起来便宜"的陷阱

中转服务的计价模式比直连官方 API 复杂,容易在这几个地方藏"猫腻":

- **是否按官方原价倍率计费,倍率是否公开**:部分服务商用不透明的"充值汇率"或"积分兑换"机制,实际单价换算下来比官方价格贵,但因为链路不直观,不容易一眼看出来
- **是否有隐藏的最低消费或过期规则**:预充值是否有有效期、账户长期不用是否被清零,这些条款经常藏在服务协议深处
- **失败请求是否计费**:请求因为上游超时或中转自身故障失败,有没有计费,这个规则直接影响服务商的信任度——好的服务商会明确写清楚失败不计费
- **计费颗粒度是否和官方一致**:比如是否精确到官方的 Token 计价规则,还是自己做了近似换算

判断方法很简单:找一个已知官方定价的模型,自己跑几十次典型请求,拿实际扣费和官方定价手动核算一遍,差异超过预期就要问清楚原因。

## 五、安全与合规边界

涉及企业级使用或者处理敏感数据的场景,这一维度权重应该拉高。具体检查项可参考[《AI API 中转的安全与合规边界》](/blog/api-relay-security-compliance/),这里只列选型时最该问的三个问题:

1. 请求内容是否会被服务商记录或用于其他用途,是否有明确的隐私政策
2. 是否支持独立 API Key、用量隔离,方便出问题时定位到具体调用方
3. 数据传输链路是否全程加密,中转节点是否有额外的存储或缓存环节

## 六、支持响应速度:遇到问题时的真实体验

前五项都是可以量化的硬指标,第六项相对主观,但同样重要——中转服务作为一个中间层,一旦出问题(比如某个模型突然不可用、计费异常),排查和响应速度直接决定业务受影响的时长。可以在试用阶段主动提一个具体技术问题,观察:

- 响应时长(几分钟内、几小时内、还是要等到第二天)
- 回复是否是针对性解决问题,还是模板话术
- 是否有清晰的状态公告渠道(而不是出问题后一片沉默)

## 七、把六个维度串成一张打分表

实际选型时,建议把上面六个维度列成表格,给候选的每家服务商打分(比如 1-5 分),权重可以按自己业务的敏感度调整(比如高并发业务把延迟权重调高,合规敏感业务把第五项权重调高):

| 维度 | 权重建议 | 自测方法 |
|---|---|---|
| 稳定性 | 高 | 1-2 周持续监控 |
| 延迟(P50/P95/P99) | 高 | 自建脚本跑并发测试 |
| 模型覆盖 | 中 | 对照自己实际需要的模型清单 |
| 计费透明度 | 中 | 手动核算实际扣费 vs 官方定价 |
| 安全合规 | 视业务而定 | 逐条核对隐私政策与协议条款 |
| 支持响应速度 | 中 | 试用期主动提问观察 |

用这张表跑一遍候选服务商,比单纯看宣传页或者朋友推荐更可靠——中转服务本质是长期依赖的基础设施,选型阶段多花一两周测试,比上线后频繁切换服务商的迁移成本要低得多。
