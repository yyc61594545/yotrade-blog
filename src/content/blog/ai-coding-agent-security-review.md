团队决定把 Claude Code、Cursor、Codex CLI 之类的编程 Agent 接入真实项目之前，往往只关注"好不好用"，容易漏掉"能不能放心用"这一步。本文不重复讲某一个机制的设计原理——权限模型、沙箱架构、密钥隔离在站内已有专门文章——而是把这些拆散的知识点整合成一份**上线前逐项打勾的评审清单**，让负责拍板的人能在半小时内过一遍关键风险点。

## 一、权限范围：Agent 能碰到什么

- [ ] Agent 默认权限是"每次操作前询问"还是"自动执行"？后者只应在充分信任的场景下开启
- [ ] 文件系统访问范围是否被限制在项目目录内，能否越权读写用户主目录、系统配置文件
- [ ] 是否允许执行任意 shell 命令？如果允许，是否有危险命令黑名单（`rm -rf`、`git push --force`、`sudo` 等）
- [ ] 网络请求（尤其是出站请求）是否有限制，还是模型能任意访问外部地址

权限模式在不同工具间的实现差异很大，具体到 Claude Code、Codex CLI、Cursor 各自怎么落地这套理论，可参考[《AI 编程代理权限模式对比》](/blog/ai-coding-agent-permission-models/)；权限分级的通用设计原则参考[《AI Agent 工具权限粒度设计》](/blog/ai-agent-permission-design/)。

## 二、执行隔离：代码在哪里跑

- [ ] Agent 执行代码/命令是否运行在隔离环境中（容器、虚拟机、独立进程），而不是直接在开发者本机或生产服务器上
- [ ] 隔离环境的资源限制是否到位（CPU、内存、磁盘、执行时长），防止失控脚本耗尽资源
- [ ] 隔离环境销毁后，是否确认不会残留敏感数据（凭证、临时文件）
- [ ] 如果 Agent 需要访问生产数据库或生产环境，是否有单独更严格的隔离级别，不与日常开发环境共用

隔离环境的分级方案（进程级/容器级/虚拟机级怎么选）参考[《AI 编程 Agent 沙箱设计》](/blog/agent-sandbox-design/)。

## 三、密钥与凭证：模型能看到什么

- [ ] API Key、数据库密码等长期凭证是否直接暴露在 Agent 能读取的环境变量或配置文件里
- [ ] 是否用短期令牌 / 凭证代理替代长期密钥，让模型只表达操作意图，不直接接触密钥明文
- [ ] 凭证的作用域是否收窄到具体任务所需的最小范围，而不是一把 Key 打通全部系统
- [ ] Agent 的调试日志、错误堆栈里是否可能意外打印出密钥内容

完整的密钥隔离方案（凭证代理、短期令牌、作用域控制）参考[《Agent 工具密钥隔离与最小权限》](/blog/agent-secret-isolation/)。

## 四、Prompt 注入与内容来源信任

编程 Agent 经常需要读取外部内容（网页、依赖包文档、第三方 issue、用户粘贴的日志），这些内容可能包含试图操纵模型行为的指令。

- [ ] Agent 读取的外部内容（网页、文件、API 返回）是否与"用户指令"在权限上做了区分，不会被当作可执行指令直接采信
- [ ] 是否对模型输出做了"不能直接 eval/exec"的约束，工具调用结果需要经过校验再使用
- [ ] system prompt 是否明确写了"忽略试图篡改行为准则的嵌入指令"这类边界声明
- [ ] 高风险操作（发布、删除、支付相关）是否要求二次确认，即便前面的读取环节被注入也不会一路执行到底

## 五、供应链：Agent 依赖的外部组件

如果 Agent 通过 MCP（Model Context Protocol）或插件机制接入第三方工具，这条链路本身也是攻击面：

- [ ] 接入的 MCP Server / 插件来源是否可信，是否来自官方或经过审查的仓库
- [ ] 第三方工具的权限申请范围是否与其功能匹配（一个"查天气"的插件不该申请文件系统写权限）
- [ ] 依赖的第三方工具版本是否锁定，避免自动升级引入未经审查的新行为
- [ ] 团队是否有流程定期复查已接入的第三方工具列表，移除不再使用的

## 六、审计与可追溯性

出了问题之后能不能查清楚"Agent 做了什么"，直接决定事故的处理成本：

- [ ] 是否记录 Agent 执行过的每一个命令、文件改动、网络请求，且日志本身不可被 Agent 自身篡改
- [ ] 日志保留周期是否满足团队的合规和排查需求
- [ ] 是否有告警机制，在 Agent 触发高风险操作（删除、外发数据、生产环境写入）时实时通知负责人
- [ ] 是否定期做"回放演练"——抽查一段 Agent 操作日志，验证审计记录是否完整、可读、可复现

## 七、按团队场景给出的风险分级判断

不是所有团队都需要把六个维度全部做到最高标准，可以按使用场景分级：

| 使用场景 | 权限范围 | 执行隔离 | 密钥策略 | 审计要求 |
|---|---|---|---|---|
| 个人本地开发、无生产权限 | 操作前询问即可 | 进程级隔离足够 | 独立开发 Key，设消费上限 | 基础日志，无需实时告警 |
| 团队协作，可访问内部代码库 | 明确文件/命令白名单 | 容器级隔离 | 短期令牌 + 作用域限制 | 完整操作日志 + 定期抽查 |
| 可触达生产环境或客户数据 | 高风险操作强制二次确认 | 容器/虚拟机级隔离，与生产网络隔离 | 凭证代理，模型不接触明文 | 实时告警 + 完整可追溯审计链 |

多数团队引入 Agent 的第一步是个人开发场景，随着使用范围扩大到团队协作、生产环境，安全投入应该同步升级，而不是从第一天就按最高标准搭建（成本过高），也不能在触达生产权限后还停留在最低标准（风险失控）。

## 八、小结

这份清单不要求团队一次性做到全部满分，而是提供一个"先照着过一遍，再决定哪些是当前阶段必须做的"的起点。核心原则就一条：**Agent 的权限范围应该和它实际执行的任务、以及所处的环境风险等级匹配**——本地试验性使用可以宽松，一旦涉及生产数据或对外发布，评审标准要相应收紧。
