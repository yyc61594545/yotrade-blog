同一段 500 字的中文产品说明，丢给 GPT-4o、Claude、文心一言分别计数，token 数可能从 700 一路跳到 1100+。差了 50% 以上——如果你按 token 计费，这就是实打实的成本差异。很多人知道"中文比英文贵"，但很少有人拆开看过：贵在哪一步？能不能省？

本文从 tokenizer 的底层机制出发，实测对比几大主流模型的中文编码效率，给出可落地的省钱判断。

## 一、tokenizer 不是都一样的

粗略理解 token 数怎么算的，可以看 [Token 到底是什么？给完全没接触过的人讲清楚](/blog/what-is-token-for-beginners/)，这里直接进差异部分。

不同厂商用不同的 tokenizer 训练语料和词表大小，这直接决定了同一段文字被切成几块：

- **BPE（Byte Pair Encoding）**：GPT 系列、Claude 用的都是 BPE 变体，核心是从字节/字符对开始，反复合并高频组合成新词元
- **词表规模**：词表越大，能塞进去的"整词"越多，罕见词被拆得越细
- **训练语料的语言分布**：如果训练语料里英文占绝对多数，词表会优先给英文常见组合分配"整词"名额，中文只能退而求其次按字甚至按字节切

这三点叠加，中文用户天然吃亏——不是模型"看不懂"中文，而是编码效率低,同样的语义信息要用更多 token 表达。

## 二、实测：同一段中文，token 数差多少

用一段 500 字左右的中文技术文档(不含代码、不含特殊符号)做测试，分别用官方 tokenizer 或近似估算工具计数：

| 模型 / tokenizer | 大致 token 数 | 相对英文膨胀系数 |
|---|---|---|
| GPT-4o (o200k_base) | ~850 | ~2.0x |
| GPT-3.5/4 (cl100k_base) | ~950 | ~2.3x |
| Claude 系列 | ~800 | ~1.9x |
| 国产大模型(中文优化词表) | ~550 | ~1.3x |

"膨胀系数"是指同样语义的中文相对英文需要多少倍的 token 才能表达。可以看到:

- cl100k_base(GPT-3.5/GPT-4 早期版本用的编码)对中文最不友好，膨胀接近 2.3 倍
- o200k_base(GPT-4o 用)做了词表升级，中文效率有明显提升
- 主打中文场景的国产模型词表天然包含大量中文常用词、成语、专业术语的整词映射，膨胀系数最低

这组数字是基于公开可验证的编码规则做的近似估算，具体到你的文本(有没有代码、专有名词、标点密度)会有波动，但相对量级是稳定的。

## 三、为什么会有这么大差距

拆开看三个具体原因：

**1. 词表里"中文整词"的数量差异**

cl100k_base 词表约 10 万，但其中中文常用词占比很低，大部分常用汉字都要拆成 2-3 个 token 才能表达一个词。国产模型词表专门针对中文语料训练，"人工智能""数据分析"这类高频词可能直接是 1-2 个 token。

**2. 标点和特殊符号的处理**

中文标点(，。！？「」)在有些 tokenizer 里没有被优化收录，会被当成生僻符号单独占用 token，进一步拉高消耗。

**3. 中英混排场景的边界损耗**

技术文档常见"使用 API 调用模型"这种中英混排，tokenizer 在中英文切换的边界处理效率往往更低，比纯中文或纯英文段落消耗更多 token。

## 四、这对成本意味着什么

如果你是按输入/输出 token 计费(参考 [2026 LLM 价格对比与选型决策](/blog/llm-pricing-comparison-2026/) 了解具体单价)，同样一段中文 prompt：

- 用 cl100k_base 编码的模型，成本比国产中文优化模型高出 60%-80%
- 长文档、批量处理场景下，这个差距会被规模放大——处理 100 万字文档，token 数差出几十万，账单差异可能是数百元级别

**判断标准**：

- 纯中文长文本处理(总结、翻译、问答)场景，优先用中文 tokenizer 效率高的模型，成本敏感度高时这条权重应该排在模型能力之前
- 中英混排的技术类任务(写代码、读英文文档),GPT/Claude 系的膨胀系数会明显收窄,tokenizer 差异不再是决定性因素
- 关于国产模型和海外模型的整体成本对比，可以看 [国产大模型 vs 海外大模型成本对比：中国开发者怎么选](/blog/cn-llm-cn-vs-overseas-cost/)

## 五、能不能自己算出准确 token 数

想在调用前精确预估成本，而不是靠经验估算，有几个方法：

1. **用官方 tokenizer 库离线计数**：OpenAI 的 tiktoken、Anthropic 提供的计数接口都支持本地跑一遍拿到精确数字，具体工具选型看 [各家 LLM token 计数库对比与选型](/blog/llm-token-counting-libraries/)
2. **完整的计算方法论**：包括如何处理中英混排、特殊符号，参考 [LLM Token 计算完整指南：tiktoken / Anthropic / 中文](/blog/token-counting-cn-guide/)
3. **批量任务先抽样**：不用每次都全量计数，抽 5-10 段有代表性的文本跑一遍，按比例外推总成本，误差通常能控制在 5% 以内

## 六、实际选型时的取舍

tokenizer 效率只是成本方程的一个变量，不是唯一变量。选模型时建议按这个顺序判断：

1. 先看任务需要的模型能力(理解力、推理能力)是否达标——能力不够,省下的 token 费也没意义
2. 能力相近的候选里，再比较 tokenizer 中文效率和单价
3. 如果是长期高频调用中文场景，中文优化词表带来的膨胀系数优势会被规模放大，值得优先考虑
4. 如果是低频调用或中英混排为主，tokenizer 差异的权重可以降低

对于通过 API 中转访问多家模型的场景，同时对接不同 tokenizer 的模型，更需要把 token 数预估这一步做扎实，避免因为编码效率差异被"隐性加价"。
