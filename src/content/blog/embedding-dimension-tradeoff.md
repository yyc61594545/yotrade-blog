选 embedding 模型的时候，大家习惯先看 MTEB 榜单排名，再看 API 单价。但一个经常被忽视的参数是**维度**——同一个模型家族往往提供多档输出维度，比如 OpenAI 的 `text-embedding-3-large` 支持从 3072 维截断到 256 维，Voyage、Cohere 也有类似设计。维度选大了浪费存储和检索延迟，选小了召回精度打折扣。这篇文章聚焦"维度怎么选"这一个具体决策，不重复讨论模型本身的调用成本对比（那部分内容见 [Embedding 模型成本对比](/blog/embedding-model-cost-comparison/)）。

## 一、维度到底影响什么

一个常见误解是"维度越高效果越好，只是贵一点"。实际情况更复杂，维度同时影响三件事，而且不是单调线性关系：

- **存储成本**：向量数据库按维度线性占用磁盘和内存。1536 维 float32 向量占 6KB，3072 维就是 12KB，千万级向量库这个差距是几十 GB 级别的实打实开销。
- **检索延迟**：近似最近邻（ANN）搜索的距离计算量随维度线性增长，高维向量在同样索引结构下查询更慢，尤其在没有做量化压缩的情况下。
- **召回精度**：维度并非越高越好。低于某个阈值（通常在 100-200 维以下）精度会明显下降，但从 768 维涨到 3072 维往往只带来个位数百分比的精度提升，边际收益递减明显。

理解这三者的非线性关系，才能做出"够用就好"而不是"堆到最大"的决策。

## 二、维度截断为什么可行：Matryoshka 表示学习

近两年主流 embedding 模型（OpenAI v3 系列、部分开源 BGE/GTE 模型）支持"维度截断"——直接取向量的前 N 维使用，效果损失远小于随机丢弃维度。这背后是 **Matryoshka Representation Learning（MRL）** 训练技巧：训练时让向量的每一个前缀子集都能独立完成检索任务，而不是只优化完整维度的表现。

这意味着：

- 一个训练时用了 MRL 的 3072 维模型，截取前 512 维依然保留大部分语义信息，而没有 MRL 训练的模型简单截断维度会掉点严重
- 使用前要确认模型是否支持 MRL 截断——不是所有 embedding 模型都天然支持，直接对不支持 MRL 的向量做截断，精度会断崖式下降
- OpenAI、Voyage、Cohere 的新一代模型 API 通常直接暴露 `dimensions` 参数，服务端截断，不需要客户端自己处理

## 三、实测取舍参考

下表是几个典型场景下维度选择的经验参考，具体数值因数据集和模型不同会有差异，仅作决策起点：

| 场景 | 建议维度 | 理由 |
|---|---|---|
| 千万级文档库，成本敏感 | 256-512 | 存储和查询成本敏感度最高，精度损失可接受 |
| 中等规模知识库（<100 万条） | 768-1024 | 精度和成本的常见平衡点 |
| 高精度场景（法律、医疗检索） | 1536+ | 召回精度优先，规模通常不会太大，成本可承受 |
| 实时性要求极高（对话内检索） | 256-384 | 查询延迟是硬约束，配合小维度 + 量化索引 |
| 离线批处理、可接受高延迟 | 完整维度 | 没有实时性约束，直接用最高精度配置 |

**做决策前建议先跑一次自己数据集上的对比实验**，而不是直接照搬别人的经验数值——不同领域文本（代码 vs 自然语言 vs 短查询 vs 长文档）对维度的敏感度差异很大。

## 四、维度压缩之外的组合手段

维度截断只是控制向量体积的一种手段，实践中通常和其他技术组合使用：

- **标量量化（int8/binary quantization）**：把 float32 压缩成 int8 甚至 1-bit 表示，存储可以再压缩 4-32 倍，代价是精度进一步下降，通常需要配合 rerank 找补
- **两阶段检索**：先用低维/量化向量做粗召回（速度快、召回多一点），再用完整精度向量或 cross-encoder 对 top-K 候选做精排，兼顾速度和精度
- **分层索引**：冷数据用低维压缩存储，热数据保留完整维度，按访问频率分层管理，这在数据规模很大但查询集中在少数热点时性价比很高

两阶段检索里的 rerank 环节和分块策略，可以参考 [中文 RAG 工程实战：从分块到 Rerank 完整流程](/blog/rag-cn-best-practices/) 里的具体做法。

## 五、如何验证维度选择是否合理

维度选择不是拍脑袋定的，建议纳入常规的 RAG 评测流程：

1. 用同一份评测集，分别跑几档候选维度（比如 256/512/1024/完整维度）
2. 记录每档的召回率（recall@K）、平均查询延迟、索引占用空间
3. 画出"精度 vs 成本"曲线，找到边际收益开始明显下降的拐点，那通常就是性价比最高的维度
4. 上线后持续监控真实查询的召回质量，而不是只信一次性评测的结果

这套评测思路和评测集构建方法，可以参考 [RAG 系统评测框架搭建实战](/blog/ai-rag-evaluation-framework/)。如果评测流程还没有自动化，也可以参考 [把模型评测接进 CI 流水线](/blog/llm-eval-in-ci-pipeline/) 把维度对比实验固化成可重复运行的脚本，而不是每次手动跑一遍。

## 六、常见误区

- **只看模型能输出的最大维度就默认用满**：多数场景下用不到完整维度带来的精度增益，白白多花存储和延迟成本。
- **换模型时沿用旧的维度设置**：不同模型家族的维度语义不同，A 模型的 512 维和 B 模型的 512 维精度表现可能差很多，换模型要重新评测。
- **对不支持 MRL 的模型做维度截断**：这是最容易踩的坑，一定先确认模型训练时是否考虑了截断场景，否则直接砍维度精度会崩。
- **忽略向量数据库自身的维度限制和索引类型影响**：不同 ANN 索引（HNSW、IVF 等）对维度的敏感度不同，选型时要一并评估，参考 [2026 向量数据库对比](/blog/vector-db-comparison-2026/)。
