编程 Agent 的评测大多聚焦"从零写代码"能力——给个需求，看谁写得又快又对。但日常工程里，重构才是更高频的场景：改一个跨文件引用、拆一个 300 行的巨型函数、把重复逻辑提取成公共方法。这类任务对 Agent 的要求和"从零生成"完全不同,更考验对已有代码结构的理解和改动边界的把控。

本文用三类典型重构任务,对比几款主流编程 Agent 的实际表现。评测方法论和设计原则可参考 [AI 编程 Agent 内部基准设计](/blog/ai-coding-agent-benchmark-design/)，具体产品间的日常使用对比看 [Claude Code vs Codex CLI 全面对比](/blog/claude-code-vs-codex-cli/) 和 [Claude Code vs Aider：两种 CLI 编程风格的对比](/blog/claude-code-vs-aider-comparison/)。

## 一、评测任务设计

选了三类在实际项目里最常见、也最容易暴露 Agent 短板的重构场景：

1. **跨文件改名**：一个被 20+ 处引用的函数/类改名，要求所有调用点、导入语句、测试文件同步更新，不漏改也不误改
2. **提取重复逻辑**：三个相似但不完全相同的函数，要求提取公共部分为可复用方法，同时保留各自的差异化分支
3. **拆分巨型函数**：一个 300+ 行、职责混杂的函数，要求按单一职责拆分成多个小函数，不改变外部调用接口和行为

每类任务在中等规模的开源项目(5-8 万行代码)上跑，人工核对改动的正确性和完整性。

## 二、跨文件改名：考验的是检索完整性

这类任务的核心风险不是"改错"，是"漏改"——遗漏一处调用点会直接导致编译或运行时错误。

| 表现维度 | 观察 |
|---|---|
| 全局检索能力 | 依赖 grep/语义搜索找全所有引用点，工具调用策略越保守(倾向多次搜索确认)的 Agent 漏改率越低 |
| 测试文件覆盖 | 部分 Agent 默认只改动业务代码，容易漏掉测试文件里的引用，需要额外提示才会覆盖 |
| 字符串/注释里的引用 | 文档字符串、日志文本里提到旧名字的情况，各家处理不一致，有的会主动更新，有的完全忽略 |

**结论**：跨文件改名任务上，表现差异主要来自 Agent 的检索策略而非"智力"本身——愿意多花几轮工具调用做交叉验证的 Agent，完整性明显更高，但相应也更慢。对准确性要求高的改名操作，建议改完后额外跑一次全局搜索确认没有遗漏,不要完全信任单次改动的完整性。

## 三、提取重复逻辑：考验语义理解而非文本匹配

这类任务不能靠简单的文本相似度判断——三段代码"看起来像"不代表逻辑等价，Agent 需要理解每段代码的实际语义差异,才能正确提取"真正公共"的部分,同时保留必要的分支逻辑。

观察到的常见问题：

- **过度提取**：把有细微逻辑差异的分支也强行合并，导致提取后的公共函数带着一堆条件判断，反而降低了可读性
- **提取不足**：过于保守，只提取了字面完全相同的代码块，遗漏了逻辑等价但写法不同的重复部分
- **破坏边界情况**：提取时遗漏了某个分支里的边界条件处理(比如空值判断)，测试跑不出来但生产环境会出问题

表现较好的 Agent 通常会在提取前先用自然语言总结三段代码的异同，再动手改，这个"先总结后改动"的中间步骤明显提升了提取的准确性。

## 四、拆分巨型函数：考验改动范围控制

这是最容易"翻车"的一类任务——巨型函数往往意味着历史包袱重、隐藏依赖多，稍有不慎就会引入行为变化。

关键观察：

- **接口稳定性**：要求外部调用接口不变的前提下，各 Agent 都能完成基本拆分，但对函数内部状态(闭包变量、副作用顺序)的处理谨慎程度差异明显
- **拆分粒度**：有的 Agent 倾向拆得很细(每个子函数 5-10 行)，有的更保守只拆出 2-3 个大块，粒度选择和用户 prompt 里的具体指引强相关——不给明确粒度要求时，结果差异较大
- **测试验证意识**：表现好的 Agent 会在拆分后主动建议或运行现有测试验证行为未变，这个习惯比"拆得漂亮"更重要,因为重构的第一原则是不改变外部行为

## 五、总结：不同重构类型对应不同的取舍

| 重构类型 | 关键风险 | 建议做法 |
|---|---|---|
| 跨文件改名 | 遗漏引用点 | 改完额外跑一次全局搜索确认 |
| 提取重复逻辑 | 过度/不足提取 | 要求 Agent 先总结异同再动手 |
| 拆分巨型函数 | 隐藏行为变化 | 明确要求跑测试验证，给出拆分粒度指引 |

没有哪款 Agent 在三类任务上全面领先，实际选择应该看你的重构场景更偏哪一类，以及团队对"谨慎但慢"和"快但需要人工复核"这两种风格的偏好。用测试先行的方式约束重构范围，是几款 Agent 上都通用的提效手段,具体做法可参考 [用 Aider 做 TDD 重构的实战](/blog/aider-test-driven-refactor/)。大规模遗留系统重构的完整实录，可以看 [AI 重构遗留单体应用实录：6 周从 40 万行代码到可维护架构](/blog/ai-refactor-legacy-monolith/)，更多重构模式总结见 [AI 重构的 10 种实战模式](/blog/ai-refactoring-patterns/)。
