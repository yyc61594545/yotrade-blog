买好 Cursor Business 席位、账号也开通了之后（购买和国内协作的具体流程见[《Cursor 团队版国内协作与账号管理完整指南》](/blog/cn-cursor-business-account/)），下一步是管理员要在后台把团队级别的配置打对。这一步经常被忽略——很多团队开完账号就直接让成员各自用默认设置，结果每个人的隐私模式、模型选择、规则文件都不一样，团队协作时经常出现"我的 Cursor 怎么和你的表现不一样"。

这篇文章只讲管理后台（Admin Dashboard）层面该配置什么，不涉及个人 `.cursorrules` 怎么写（那部分见[《.cursorrules 最佳实践》](/blog/cursor-rules-best-practices/)），聚焦"作为管理员，团队统一标准应该怎么定"。

## 一、隐私模式：团队级强制，而不是靠自觉

Cursor 的 Privacy Mode（隐私模式）决定了代码内容是否会被用于模型训练、是否会被留存。个人版可以自己开关，但团队场景下，这不该是"建议每个人开启"，而应该在管理后台强制锁定：

- 进入 Team/Business 管理后台的 Privacy 设置项，把隐私模式设为团队强制（Enforced），成员端不能自行关闭
- 涉及客户代码、未公开业务逻辑的仓库，这一项基本是硬性合规要求，不是可选项
- 强制开启后，部分依赖云端索引缓存的功能（比如跨会话的长期记忆）可能会受限，需要提前和团队说明取舍

管理员如果只是口头要求"大家记得开隐私模式"，长期来看一定会有人忘记，唯一可靠的方式是后台强制锁定。

## 二、模型访问白名单

Business 版后台可以配置团队成员能使用哪些模型。这一项容易被忽略，但至少有两个现实理由需要主动配置，而不是全部放开：

- **成本控制**：不同模型的调用成本差异很大，全部放开容易出现成本失控，具体成本对比可以参考[《Claude Code 与 Cursor 成本对比》](/blog/claude-code-vs-cursor-cost/)，据此决定哪些模型该限制给特定角色使用
- **输出一致性**：如果团队约定"代码生成统一用某个模型"，但后台没有限制，成员各自切换模型，代码风格和质量会参差不齐，Review 阶段的沟通成本会上升

配置路径通常在 Admin Dashboard 的 Models 设置里，可以按角色或按项目组分别设置可用模型列表，而不是团队全员一刀切。

## 三、Codebase Indexing 排除规则

Cursor 会对代码库建索引以支持语义搜索和上下文理解，但不是所有目录都该被索引：

- `node_modules`、构建产物、`.git` 这类目录默认应该排除，避免索引噪音拖慢检索质量
- 含密钥、配置模板的目录（比如 `.env.example` 之外的实际密钥文件，虽然一般不会入库，但如果历史遗留有敏感文件，务必主动排除）
- 大型二进制资源目录（设计稿、模型权重文件）索引价值低，还会拖慢索引速度

这些排除规则可以在项目根目录的 `.cursorignore` 文件里配置，但团队场景下更推荐把 `.cursorignore` 作为项目脚手架的标配文件统一提交进仓库，而不是靠每个成员自己记得加，这样新成员 clone 仓库后天然继承规则。

## 四、规则文件的统一分发

个人写 `.cursorrules` 或 `.cursor/rules/*.md` 的方法论已经有专门文章讲过，团队场景下的额外问题是：**怎么保证所有成员用的是同一份规则，而不是各自本地攒了一份"祖传配置"**。

推荐做法：

1. 把 `.cursor/rules/` 目录作为项目仓库的一部分提交进 git，和代码一起被 clone、被 code review，而不是放在成员本地全局配置里
2. 规则文件的修改走正常 PR 流程，团队对"新增一条规则"要有共识，不是谁想加就加
3. 如果有跨项目通用的规则（比如统一的代码风格、commit message 规范），可以抽成独立的规则片段，在多个仓库间复制维护，管理后台目前不支持跨仓库的规则同步，需要人工维护一致性

这一条看似是流程问题，但直接决定了团队用 Cursor 产出的代码风格是否统一——规则文件不统一，Agent 生成的代码风格也不会统一。

## 五、审计日志与用量看板

Business 版后台提供成员用量和部分操作的审计日志，管理员至少要养成定期看两类数据的习惯：

- **用量分布**：哪些成员/项目组的调用量异常高或异常低，异常高可能是滥用或效率问题，异常低可能是团队没真正用起来
- **模型调用分布**：是否有成员绕过白名单尝试使用未授权模型（多数情况下后台会直接拦截，但日志能反映尝试次数，侧面说明白名单设置是否合理）

这部分数据建议每月抽查一次，配合团队推广节奏参考[《Cursor 团队推广三个月复盘》](/blog/cursor-team-rollout-3months/)里的经验，用量数据是判断推广是否真正落地的硬指标，比"大家反馈还不错"更可靠。

## 六、配置检查清单

管理员可以按下面顺序过一遍，确认团队级配置是否到位：

| 配置项 | 检查内容 | 优先级 |
|---|---|---|
| 隐私模式 | 是否已强制锁定，成员无法自行关闭 | 高 |
| 模型白名单 | 是否按角色/项目组限制了可用模型 | 中 |
| `.cursorignore` | 是否已作为脚手架文件纳入代码库 | 中 |
| 规则文件分发 | `.cursor/rules/` 是否入库、走 PR 流程 | 中 |
| 用量审计 | 是否有固定周期的人工抽查 | 低 |
