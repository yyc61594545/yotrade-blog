网页上弹出一句"模型当前处于满载状态""We're experiencing high demand"或者干脆一个英文的 at capacity，很多人的第一反应是刷新、换浏览器、重装 App，折腾半小时才发现问题根本不在自己这边。这篇只讲一件事：**怎么在三十秒内判断这句提示是谁的问题，以及对应该做什么**。

## 一、"满载"到底是什么意思

"满载"（at capacity / high demand）是服务端主动给出的降级信号：这一刻请求某个模型的人太多，调度系统拿不到空闲算力，于是先把一部分请求挡在外面。它的三个特征决定了处置方式：

- **它和你的账号无关**。不是你被限制了，同一时刻隔壁用免费号的人可能也在看同一句话。
- **它是分模型的**。满载通常只落在某一个具体模型上（最常见是当期最强的推理模型），同账号切到上一代模型往往立刻能用。
- **它是分钟级的**。这类拥塞一般几分钟到几十分钟就过去，不需要任何操作就会自己恢复。

真正要紧的是：有四种完全不同的情况会让你看到"看起来差不多"的提示，而它们的处置动作截然相反。认错了就会白折腾。

## 二、四种提示的对照表

先对着下面这张表把你看到的原话归类，这是整篇文章最有用的部分：

| 你看到的提示 | 真实原因 | 和账号有关吗 | 该做什么 |
| --- | --- | --- | --- |
| 模型满载 / high demand / at capacity | 服务端算力拥塞 | 无关 | 换模型，或等几分钟 |
| 你已达到本次对话上限 / usage limit reached，并给出一个恢复时间 | 你的套餐额度用尽 | 有关 | 看恢复时间，换模型或等窗口重置 |
| 网络错误 / something went wrong，刷新后随机复现 | 本地网络或出口被拦 | 无关 | 换网络环境测试 |
| 账号被限制 / 要求重新验证身份 | 风控命中 | 有关 | 停手，别反复重试 |

判断的关键是**看提示里有没有"时间"和"你"**：带明确恢复时间的，是你的额度问题；只说需求高、不提你的账号的，是服务端的问题。这两类的处理完全不同——前者等了也没用（除非等到窗口重置），后者等几分钟就好。

## 三、满载时最有效的一步：换模型

真满载的场合，九成情况下换模型立刻就能继续工作，这比刷新页面有用得多。

对话框上方（或输入框左侧，取决于你用的客户端版本）有模型选择器，往下退一档——从当期旗舰推理模型退到上一代、或者退到更轻量的快速模型。拥塞几乎总是集中在最新最强的那一个上，因为所有人都在抢它。

一个容易被忽略的细节：**切模型不会丢掉当前对话**。你可以在同一个会话里换模型继续问，上下文还在。所以不用新开窗口，更不用把问题重新复制粘贴一遍。

如果你的工作确实非某个模型不可（比如要那个模型特有的长上下文），那就只能等。这种情况下别开着页面反复点重试——每次重试都是一个新请求，排不到就是排不到，手动刷新并不会让你插队。

## 四、Codex 和命令行里的"容量不足"

Codex、Claude Code 这类跑在终端里的工具遇到同样的服务端拥塞，提示会更像一个报错，常见是 HTTP 429 或 503 配一句模型不可用。这里有个判断要点：

- **429** 往上通常是"请求太多"，可能是服务端拥塞，也可能是你自己的用量窗口满了——要看响应里有没有带 `retry-after` 或者额度相关字样。
- **503 / 529** 基本都是服务端侧，和你无关，重试就行。

命令行工具一般自带重试，但默认策略保守。如果你是自己写脚本调接口，重试要用**指数退避加随机抖动**，不要固定间隔死磕——一堆客户端同步重试会把拥塞拖得更久：

```python
import random, time
import httpx

def call_with_backoff(client, payload, max_retries=5):
    for attempt in range(max_retries):
        r = client.post("/v1/responses", json=payload)
        if r.status_code not in (429, 503, 529):
            return r
        # 优先尊重服务端给的 retry-after
        wait = float(r.headers.get("retry-after", 0))
        if wait <= 0:
            # 指数退避 + 抖动，避免所有客户端同时回来
            wait = min(2 ** attempt, 32) + random.uniform(0, 1)
        time.sleep(wait)
    raise RuntimeError("上游持续不可用，建议降级到备用模型")
```

脚本层面真正该做的是**降级而不是死等**：重试几次还不行，就自动切到备用模型把任务做完，而不是让整个流程卡死。至于限流本身的识别和处理，[Codex 变慢与降智的常见原因排查（限流、风控、号池）](/blog/cn-codex-rate-limit-throttling/) 讲得更细。

## 五、怎么确认不是自己网络的问题

国内用户最容易混淆的就是服务端拥塞和自己的网络被拦。两者都表现为"用不了"，但一个等等就好，一个等到天亮也没用。三十秒自测：

1. **换一个网络环境**。手机流量、家里宽带、公司网络里换一个试。如果只在某一个环境下报错，那就是网络问题，不是满载。
2. **看提示语本身**。满载提示是服务端正常返回的页面文案，通常中英文规整、带产品语气；网络被拦更多是浏览器层面的连接失败、超时、或者一个裸的英文报错。
3. **试一下另一个模型**。能换模型正常回答，说明连接是通的，确实只是那个模型挤。

如果判断是网络侧，那是另一类问题了，和满载无关。相关排查可以看 [ChatGPT Windows 桌面版打不开或消息发不出去的排查](/blog/cn-chatgpt-windows-app-not-opening/)。

## 六、付费套餐能不能避开满载

半能。各档付费套餐在官方说明里都包含"高峰期优先访问"（priority access），意思是拥塞时付费用户排在免费用户前面。实际体验是：**付费号遇到满载的概率明显更低，但不是零**——全网级别的拥塞，谁都挡不住。

这里要分清两件常被混为一谈的事：

- **满载**是算力拥塞，付费只能提高你的优先级。
- **限额**是套餐本身的用量上限，付费档位越高上限越高，这是实打实的额度差异。各档的窗口怎么算，看 [ChatGPT 各套餐的 5 小时与每周限额怎么计算](/blog/cn-chatgpt-usage-limit-reset-rules/)。

所以如果你是因为**反复撞限额**才考虑升级，那升级确实有用；如果你只是偶尔碰到满载，升级的收益没你想的那么大，换个模型就过去了。

## 七、什么情况要停手

有一类提示看起来像满载，其实是风控，**继续重试会让情况变坏**。特征是：

- 提示里出现账号、验证、异常活动这类字眼，而不是需求、容量、繁忙。
- 换模型、换网络、换设备都是同一句话。
- 其他账号在同一网络下能正常用，只有你这个号不行。

这三条同时成立，基本可以确定是账号侧的问题，此时该做的是**停下来**，不要在十分钟里重试几十次——高频失败请求本身就是风控信号，会把一个可能自己恢复的临时限制坐实成长期的。回答质量突然变差而不是直接报错的情况，另见 [ChatGPT 突然不思考、回答变差：先排查这几项](/blog/cn-chatgpt-reasoning-quality-drop/)。

## 八、一句话流程

把上面的内容压缩成一个可以背下来的顺序：

1. 读提示原话，看有没有"你的账号"和"恢复时间"——有就是限额，没有就往下走。
2. 换一档模型，能用就继续工作，问题结束。
3. 还不行，换个网络环境试一次，确认不是本地连接问题。
4. 确认是服务端拥塞，去干别的，十分钟后回来，不要反复刷。
5. 提示里出现账号/验证字样，立刻停手，别重试。

绝大多数"满载"在第 2 步就解决了。会浪费时间的，往往是把第 1 步跳过去的人。
