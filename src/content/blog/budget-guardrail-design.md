预算告警的阈值分层和熔断响应机制，[AI API 预算告警与自动熔断](/blog/llm-budget-alerting/) 已经讲得很细；预算上限在请求层、用户层、全局层的具体实现，[AI API 预算上限自动化设计](/blog/ai-api-budget-cap-design/) 也覆盖了。本文不重复这些内容，聚焦两个经常被忽视的问题：护栏该放在调用链的哪一层，以及——护栏写了之后，你怎么知道它真的会生效。

## 一、护栏放在哪一层，决定了它能挡住什么

同一个"超支阻断"需求，放在不同位置能挡住的风险完全不一样：

| 位置 | 能挡住 | 挡不住 | 延迟代价 |
|---|---|---|---|
| 客户端/SDK 层 | 明显异常的高频调用、循环 bug | 恶意绕过客户端检查、多端并发叠加超支 | 几乎为零 |
| 网关/中转层 | 跨客户端的总量超支、多用户并发叠加 | 单次请求本身的异常大小（除非做预检） | 一次网络往返 |
| 模型厂商账单层 | 最终兜底，怎么都跑不出去 | 已经发生的超支——只能事后止损，钱已经花出去了 | 通常有账单延迟，不是实时 |

**实践判断**：只在一层设护栏几乎必然出问题。客户端层拦不住绕过 SDK 的直接调用，网关层拦不住网关自身故障时的失控请求，厂商账单层永远是"事后"的。稳妥的做法是三层都设，但职责不同——客户端层做体验优化(尽早失败,不浪费一次网络往返)，网关层做实际的强制阻断(这是真正兜底的一层)，厂商账单层做最终对账和异常检测。

如果你通过 API 中转访问多个模型厂商，护栏更应该收敛在中转层统一实现，而不是让每个厂商各自的限额机制来兜底——厂商侧的限额通常是月度/账户级别的粗粒度控制，响应不够实时,也没法按你自己的业务逻辑(比如按客户、按功能模块)做细粒度阻断。

## 二、护栏没测试过，等于没有

这是最容易被忽视的一点：团队通常会为业务逻辑写单元测试，但很少有人真的测试过"超支阻断触发时,系统的行为是否符合预期"。护栏和普通功能代码不一样——它只在极端情况下触发，平时的正常流量完全走不到这条路径，这意味着一个写错的护栏可以在代码库里安然无恙地躺很多个月，直到真正超支的那天才暴露问题,而那时候已经晚了。

**建议的验证方式**：

1. **注入式测试**：在测试环境里人为构造"已经接近阈值"的状态，验证下一次请求确实被拦截，而不是等真实流量撞上去才发现
2. **边界值测试**：阈值刚好等于、刚好超过、刚好低于临界点时的行为分别是什么——这类边界条件是最容易写错的地方
3. **护栏失效的降级路径也要测**：如果护栏依赖的计数服务本身挂了，是该"默认放行"还是"默认拒绝"？这个选择要显式做出，不能是未定义行为。默认放行意味着护栏故障时失去保护,默认拒绝意味着护栏故障会变成一次可用性事故——两者各有代价,需要按业务重要性提前决定
4. **定期演练**：把护栏测试纳入定期回归的范围，而不是上线时测一次就再也不管——阈值配置、业务逻辑都会随时间变化，护栏代码本身也可能被无意中改坏

## 三、阻断后的用户体验，不只是返回一个错误

技术上"挡住超支"只是第一步，阻断发生后系统怎么响应同样重要：

- **区分阻断原因**：是这个用户/客户自己的额度用完了，还是全局预算触发了熔断？两种情况给用户看到的提示应该不同,处理路径也不同——前者是用户自己该知道的账户状态,后者可能需要平台方介入
- **不要用生硬的 500 报错**：预算阻断是可预期的业务状态，不是系统故障，应该返回明确的业务错误码和可读提示，方便调用方(可能是另一个自动化系统)做针对性处理而不是简单重试
- **给出恢复路径**：告诉用户/调用方额度什么时候重置、怎么申请临时提额，而不是让请求悄无声息地失败

## 四、护栏配置本身要有变更审计

护栏的阈值、规则不是一次写死就不变的,会随着业务规模调整。但正因为护栏平时"看不见"，它的配置变更也容易缺乏审计——谁在什么时候把某个客户的阈值从 100 提到了 1000，如果没有记录,出问题时排查会很痛苦。护栏配置变更应该和代码变更一样走版本控制和审批流程，不能是后台数据库里悄悄改一个数字。

## 五、小结：护栏设计的三个问题清单

1. **放在哪层**：客户端、网关、厂商账单层各自负责什么，是否有单点失效风险
2. **测过吗**：护栏触发路径是否被真实测试覆盖过，护栏自身故障时的降级行为是否明确
3. **阻断之后呢**：用户体验、恢复路径、配置变更审计是否完整
