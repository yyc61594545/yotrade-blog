编程 Agent 这个赛道过去一年多的变化，与其说是"哪家更强"，更值得关注的是产品形态本身的分化——同样是"让 AI 写代码"，落地方式已经明显走出了四条不同的路线，各自的假设、约束和适用场景都不一样。这篇是基于公开信息和日常使用观察的个人整理，不做具体市场份额或融资数字的断言，重点放在形态差异对选型的影响上。

## 一、形态一：终端原生型（Claude Code、Codex CLI、Aider）

这一类的共同特征是没有独立的图形界面，直接跑在终端里，靠命令行和文件系统交互。代表产品是 Claude Code、OpenAI 的 Codex CLI、开源的 Aider。

核心假设是：开发者已经有自己习惯的编辑器（Vim、Neovim、甚至就是 VS Code），不需要 Agent 再提供一套编辑体验，Agent 只负责"理解任务、改文件、跑命令、验证结果"这个闭环。这类工具往往权限模型更直接——文件读写、命令执行的权限颗粒度做得比较细，适合放进 CI 或者无人值守的自动化流程。

这类形态的优势在于组合灵活，可以嵌入现有的 shell 脚本、CI pipeline，劣势是没有可视化的 diff 预览等 IDE 特有的交互细节，重度依赖图形界面辅助判断（比如复杂的多文件重构）时体验不如 IDE 原生型。

## 二、形态二：IDE 原生型（Cursor、Zed、Windsurf）

这一类是把 AI 能力做进编辑器内核，不是外挂插件。Cursor 基于 VS Code 二次开发，Zed 是从零写的 Rust 编辑器原生集成（配置方法可参考 [Zed AI 助手配置](/blog/zed-ai-assistant-config/)），Windsurf 走的也是类似路线。

这条路线的假设是：AI 辅助编程需要跟编辑器的语义理解（LSP、AST、跨文件引用）深度绑定，才能做到"精确知道要改哪里"，外挂插件因为拿不到编辑器内部的完整上下文，天然有一层信息损耗。实际体验上，IDE 原生型在"选中一段代码直接改"（Inline Assist 类交互）上普遍比插件型更流畅，因为不需要额外的进程通信开销。

这条路线的行业整合动作值得关注——多个原生编辑器项目之间出现过并购或合并传闻（相关分析见 [Cursor 与 Windsurf 并购传闻观察](/blog/cursor-vs-windsurf-acquisition/)），背后的逻辑是编辑器本身的护城河没有想象中高，真正的竞争力落在模型调用效率和上下文管理这些工程细节上,单纯"重写一个编辑器"的边际收益在下降,所以行业出现整合倾向——这是基于公开信息的个人判断，不代表确证的商业结论。

## 三、形态三：插件型（Cline、Roo Code、GitHub Copilot Chat）

不重写编辑器,而是以扩展形式接入现有编辑器生态,以 VS Code 生态最典型。Cline 是这条路线里社区活跃度较高的代表(配置详见 [Cline 在 VS Code 的配置](/blog/cline-vscode-config-guide/))。

这条路线的假设是:开发者的编辑器选择成本很高(团队统一工具链、插件生态、个人习惯),不应该为了用 AI 功能换编辑器,所以把 AI 能力做成"可插拔"的扩展更容易被采纳。代价是插件型天然受限于宿主编辑器暴露的 API 能力,某些深度集成(比如原生的多文件 diff 渲染)做起来比原生型更别扭,需要绕更多弯路模拟原生体验。

这条路线目前看起来是最"平权"的——不绑定特定编辑器厂商,开源实现多,门槛低,个人开发者和小团队接入成本最低。

## 四、形态四:后台异步型(Cursor Background Agent、类 Devin 产品)

前三种形态都是"人在场"的交互模式——开发者发出指令,等待几秒到几十秒拿到结果,过程中随时可以打断介入。第四种形态反过来:把任务扔给 Agent,人离开,Agent 在后台(通常是隔离的云端环境或容器)自主执行一段较长时间(几分钟到几十分钟),完成后以 PR 或者总结的形式交回。Cursor 的 Background Agent 是这个方向上比较典型的产品化尝试(具体案例可参考 [Cursor Background Agent 实战案例](/blog/cursor-background-agent-cases/))。

这条路线的假设最激进:相信 Agent 不需要人全程盯着就能完成有意义的独立任务。目前从公开的使用反馈看,这类产品在边界清晰、验证标准明确的任务上(比如"把这个依赖升级到新版本并修掉编译错误")完成度不错，但在需要持续判断、目标本身模糊的任务上，独立运行的风险（跑偏、过度修改）比前三种形态更高，需要更强的权限约束和事后审查机制作为兜底。

## 五、四种形态不是互斥关系,是分工

从日常观察看,同一个开发者/团队往往同时用多种形态,按任务类型分工,而不是"选一个押注到底":

| 任务类型 | 更适配的形态 |
|---|---|
| 日常交互式编码、调试 | IDE 原生型 / 插件型 |
| CI 里自动修复 lint / 简单 bug | 终端原生型 |
| 大范围机械式重构(升级依赖、改命名规范) | 后台异步型 |
| 团队统一工具链,不想强制换编辑器 | 插件型 |

具体到重构类任务,不同形态的实际表现差异可以参考 [编程 Agent 重构任务横评](/blog/coding-agent-refactor-bench/) 里的实测对比。

## 六、格局分化背后的一个共同瓶颈:模型调用的稳定性

不管产品形态怎么分化,底层都要依赖大模型 API 的稳定调用——这是四种形态共同的基础设施依赖,而不是差异点。国内开发者用这些工具时经常先撞上网络和账单的问题,而不是产品本身的能力问题,这也是为什么中转服务这类基础设施在国内的编程 Agent 生态里扮演了不太起眼但必要的角色。
