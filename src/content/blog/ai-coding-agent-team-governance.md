个人用 Claude Code 或 Cursor 写代码，配置随意一点问题不大——出了岔子自己兜底。但一旦扩展到十几人、几十人的团队，每个人对"该给 Agent 多大自主权""AI 写的代码要不要额外评审""出问题算谁的责任"理解不一样，治理真空会比工具本身的能力上限更早成为瓶颈。这篇文章聚焦"治理规则怎么定"，不重复讨论具体工具的权限模式差异或落地踩坑经验，那部分可以参考 [AI 编程代理权限模式对比](/blog/ai-coding-agent-permission-models/) 和 [团队引入 AI 编程的踩坑](/blog/ai-coding-team-adoption/)。

## 一、为什么需要专门的治理规则

没有治理规则的团队常见的失控表现：

- **每个人的 Agent 自主权限配置完全不同**：有人开了自动执行所有命令的模式，有人事事需要确认，团队协作时互相不知道对方的 Agent 能做到什么程度
- **AI 生成的代码和人写的代码走一样的评审流程**，但评审者不知道该用什么心态审——是当作"实习生写的代码要仔细看"还是"工具生成的可以放松"，标准不统一导致该拦住的问题溜过去，或者不该卡的地方过度谨慎拖慢流程
- **出问题后无法定位是模型的问题还是使用方式的问题**，因为没有留痕，复盘只能靠回忆
- **敏感操作（改生产配置、动数据库迁移脚本）没有明确谁能让 Agent 自主执行、谁必须人工审批**

治理规则的目标不是限制 Agent 的能力，而是让"自主权有多大"这件事变得可预期、可追溯、可复盘。

## 二、自主操作分级：不是所有操作都该一视同仁

给 Agent 能执行的操作按风险分级，是治理规则的核心。一个可参考的三级框架：

| 级别 | 操作类型 | 治理要求 |
|---|---|---|
| 低风险 | 读代码、跑测试、本地格式化、生成文档 | 完全自主，无需审批，鼓励尽量自动化 |
| 中风险 | 写代码改动、提交本地 commit、跑 lint/build | 自主执行，但改动必须经过正常的 PR 评审流程才能合并 |
| 高风险 | push 到主分支、改生产配置、执行数据库迁移、发布部署、删除文件/分支 | 默认禁止 Agent 自主执行，需要人工在场确认，且操作前展示将要执行的具体命令 |

这个分级思路和个人使用时的安全习惯是一致的——比如"push、reset --hard、跳过 hooks 一类操作需要人工确认"——团队治理规则本质上是把这类个人经验固化成团队统一执行的书面规范，而不是让每个人凭直觉判断。

具体到工具配置层面（哪些命令加白名单、哪些需要权限确认弹窗），可以参考 [AI 编程代理权限模式对比](/blog/ai-coding-agent-permission-models/) 里几个主流工具的实现差异，选一个团队统一遵循的基线配置。

## 三、AI 生成代码的评审标准

AI 生成的代码不应该被当作"信任担保过的代码"直接合并，也不该被当作"需要额外怀疑"的代码过度审查——合理的标准是**用和人写代码一样的门槛，但检查重点略有不同**：

- **正常门槛照旧**：单元测试覆盖、代码风格、性能影响、安全扫描，这些标准不因为代码是 AI 生成的就放松
- **额外关注的重点**：
  - **是否存在"看起来对但实际没测过"的边界情况**——Agent 有时会生成语法正确、逻辑看似合理但没有真正验证过的代码路径
  - **是否引入了不必要的依赖或抽象**——模型倾向于"过度设计"，评审时要留意是否有可以简化的部分
  - **敏感信息是否被带入了 diff**——比如调试过程中模型可能把日志、临时凭证误写进代码
- **评审者要知道这段代码是 AI 生成的**：PR 描述或 commit message 里标注清楚（比如统一用 `Co-Authored-By` 或专门的标签），让评审者带着合适的关注点去看，而不是完全不知情

## 四、审计留痕：出问题时要能回答"发生了什么"

治理规则要求的留痕，不是为了监控员工，而是为了在出问题时能快速定位根因、复盘改进。至少应该留存：

- **每次 Agent 执行的高风险操作**：命令内容、执行时间、执行者、审批记录（如果有）
- **PR 层面的 AI 参与标记**：哪些改动是 Agent 生成、经过何种程度的人工修改
- **异常终止记录**：Agent 因为权限拦截、命令失败、用户手动中断而未完成的操作，尤其是那些"本该执行但没执行成功"的高风险操作，容易被忽视但排查事故时很关键

审计日志不需要多复杂的系统，很多团队直接用现有的 CI 日志 + git 历史 + 一个简单的操作记录表就能满足基本需求，关键是"规则要求必须留"，而不是等出事了才想起来查不到记录。

## 五、事故响应：出问题之后怎么办

治理规则要提前定义好事故响应流程，而不是出事之后现场讨论：

1. **发现异常立即暂停该 Agent 会话**，避免在排查过程中问题被进一步放大
2. **区分责任类型**：是模型输出有问题（幻觉、误判），还是权限配置给得过宽，还是人工审批环节被跳过——这决定了后续该收紧哪个环节
3. **复盘后更新治理规则本身**：事故往往暴露的是分级或审批流程的漏洞，规则要能迭代，而不是一成不变的文档
4. **明确对外沟通口径**：如果事故影响到了生产环境或客户，要有清晰的沟通责任人，不能因为"是 AI 做的"就模糊了责任归属——最终责任始终在使用 Agent 的人和审批链条上，不在工具本身

安全评审的具体检查清单可以参考 [AI 编程 Agent 安全评审清单](/blog/ai-coding-agent-security-review/)，把治理规则和上线前检查结合起来形成闭环。

## 六、成本与用量也是治理的一部分

治理规则不只覆盖安全和质量，也应该包括资源使用的边界：

- **明确团队/项目的用量预算**，避免个别高频用户的调用量挤占整体预算，具体分配方法可参考 [团队 LLM 预算分配实战](/blog/llm-team-budget-allocation/)
- **成本控制策略要写进治理规则**，比如哪些场景鼓励用更便宜的模型、哪些场景允许用最强模型不计成本，避免每个人凭感觉选择，参考 [AI 编程代理成本控制实战](/blog/ai-coding-agent-cost-control/)
- **多人共享的 API key 要做好用量隔离**，方便按团队或项目拆分账单和监控异常消耗

## 七、落地建议：从最小规则集开始

治理规则不需要一次性写得面面俱到，容易导致规则太重没人遵守。建议的落地节奏：

1. **先定义高风险操作清单**（哪些命令/操作必须人工审批），这是最容易出严重问题的部分，优先级最高
2. **接着统一 AI 生成代码的标注和评审流程**，让评审有据可依
3. **补上审计留痕的最小实现**，哪怕只是一个共享表格，先有比没有强
4. **运行一段时间后**，根据实际遇到的问题（而不是假想的风险）逐步补充规则细节，避免过度设计一套没人会真正照做的流程

## 八、常见误区

- **治理规则只写给管理层看，实际配置没人落地**：规则必须体现在实际的工具配置和 CI 门禁里，不能只是一份 wiki 文档。
- **对所有操作用同一套审批流程**：高风险和低风险操作用同样的审批力度，要么拖慢日常工作，要么让真正危险的操作也被"习惯性放行"。
- **把"AI 生成"当作免责理由**：出问题时责任依然在审批和使用的人身上，治理规则要清楚地传达这一点。
- **规则定完就不再更新**：工具能力和团队使用模式都在快速变化，治理规则需要定期（比如每季度）复盘调整。
